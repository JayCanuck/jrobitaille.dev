# Decisions

ADR-lite. D1 to D3 are locked; D4 onward are defaults that cost one edit to change. Add a new entry rather than rewriting an old one.

## D1: Framework is Next.js 16 static export

- **Date:** 2026-10-04 · **Status:** locked
- **Context:** A three-page static site. Astro 7 is the better pure-static fit (zero JS by default); TanStack Start and React Router framework mode were also weighed.
- **Decision:** Next.js 16 App Router with `output: 'export'`, React Compiler on, nearly everything a Server Component.
- **Why:** Next.js is the most-requested React framework in full-stack roles and a public artifact is the honest way to claim it. The cost (a framework bigger than the site, roughly 80 to 120 KB of runtime JS) is real and is mitigated by keeping client code to a few deliberate islands and saying so in the README.
- **Consequences:** No middleware, ISR, or default image loader (`images.unoptimized`); dynamic routes need `generateStaticParams`. None of these bite this site.

## D2: Hosting is Cloudflare Workers static assets

- **Date:** 2026-10-04 · **Status:** locked
- **Context:** GitHub Pages is free and simple but has no custom headers, no cache control and no branch previews.
- **Decision:** Cloudflare Workers static assets with the `jrobitaille.dev` zone on Cloudflare nameservers; deploy from GitHub Actions with `cloudflare/wrangler-action`. Phase 1 serves the `*.workers.dev` URL only; the custom domain moves over in Phase 5.
- **Why:** `_headers` for CSP and caching, preview URLs per PR, free cookieless Web Analytics, free bulk redirects for the `.com` and `.cv` domains.
- **Consequences:** Analytics is Cloudflare Web Analytics plus Google Search Console; no Google Analytics (50 to 100 KB of JS and a consent question for no gain).

## D9: Toolchain currency: ESLint 10, TypeScript 6, tsgo shadow job, Dependabot pins

- **Date:** 2026-10-04 · **Status:** default
- **Context:** ESLint 10 is current, but eslint-plugin-jsx-a11y, eslint-plugin-react and eslint-plugin-import still declare peer ranges that stop at 9 and call context APIs that 10 removed. TypeScript 7 (the native compiler) ships without the JavaScript compiler API until 7.1, which typescript-eslint and `next build` type-checking need.
- **Decision:** ESLint 10 with eslint-config-next 16 as the base, since it declares `eslint >=9` and bundles the plugins; no direct jsx-a11y dependency, its strict rule set is layered on from the bundled instance, and the bundled react, import and jsx-a11y rules are wrapped with `@eslint/compat` `fixupPluginRules` until they support 10 natively. TypeScript 6.0 as the bridge release. A non-blocking CI job runs the TypeScript 7 native compiler on every PR as stage one of a staged migration. Dependabot groups minor and patch npm updates into one weekly PR and ignores major updates for `typescript` (until 7.1 plus typescript-eslint support) and `@types/node` (tracks the pinned Node major).
- **Consequences:** The fixup block in `eslint.config.mjs` is deleted once the plugins catch up. When 7.1 lands, the shadow job becomes the blocking typecheck and the Dependabot ignore for `typescript` goes. `@types/node` moves with `.nvmrc`.

## D10: No browserslist field; CSS stays external

- **Date:** 2026-10-04 · **Status:** default
- **Context:** SPEC §6 targets evergreen browsers (last 2 of Chrome, Edge, Firefox, Safari). Next 16.3.8 compiles against a modern default (Chrome, Edge, Firefox 111 and Safari 16.4) when no `browserslist` is set. Correction (2026-10-05): the Turbopack static export does emit a legacy polyfill chunk, about 40 KB gzipped, behind `nomodule`, which evergreen browsers never fetch; the Lighthouse legacy-JavaScript finding refers to Next's separate, unconditionally loaded polyfill module, not to that chunk. Measured from a clean cache: explicit evergreen versions SWC knows (for example `chrome 150`, `safari 26`) reproduce the default output byte for byte (565,368 B raw, 170,007 B gzip), while a `last 2 versions` query resolves to releases the bundled SWC compat table does not know yet (Chrome 153 to 154, Safari 27) and makes SWC down-level everything: 608,547 B raw, 180,878 B gzip, 11 KB more over the wire. Browsers release monthly, so that query will keep outrunning the table.
- **Decision:** No `browserslist` field. The default target already matches the evergreen intent with the smallest output; a pinned explicit list would only drift. Revisit if Next changes its default or SWC starts tracking current releases.
- **Decision, CSS:** The ~30 KB Tailwind stylesheet stays an external `<link>` rather than being inlined with `experimental.inlineCss`. Inlining would recover roughly 4 mobile Lighthouse performance points on first load but requires `style-src 'unsafe-inline'`; the strict `style-src 'self'` CSP in `_headers` (Phase 3) is worth more on a site recruiters read with DevTools open, and the stylesheet is cached for returning visitors.
- **Consequences:** The performance budget in AGENTS.md is met without either change. If a future audit shows LCP over budget on throttled 4G, inlining is the first lever to re-evaluate, together with a nonce or hash-based CSP.

## D14: Design system, motion policy and security headers

- **Date:** 2026-10-05 · **Status:** default
- **Context:** Phase 3 turns the structured page into the finished site: "technical, quiet, with personality", crisp where recruiters scan, personality where they linger. Everything stays static; no new client components.
- **Fonts and type:** Geist (variable sans, body) and Geist Mono (labels, dates, the timeline rail) through `next/font`. Fluid type as `--text-*` tokens with `clamp()`; prose capped near 72ch, the work grid and timeline on a wider column.
- **Palette and accent:** a slate-and-white family with one accent, "Ultraviolet" (`oklch(0.56 0.2 300)` light, `oklch(0.76 0.14 300)` dark), chosen over a warm tangerine candidate at the design checkpoint. `--brand` is for fills, rails and rings; `--brand-text` passes AA on each background. Dark mode follows `prefers-color-scheme` (D4). shadcn variable names are kept so the primitives keep working.
- **Voice:** section headings carry it: "Hello", "Things I've shipped", "Where I've been", "Toolbox". A tagline slot under the hero and a playful footer-line slot live in `src/content/site.ts`; empty strings render no element. The 404 brings back the UFO and cow over the previous site's backdrop.
- **Motion:** texture, not a show. The cover band drifts with `animation-timeline: scroll()`, timeline nodes reveal with `animation-timeline: view()`, the UFO floats; all inside `@supports` and `@media (prefers-reduced-motion: no-preference)`, so unsupported browsers and reduced-motion users get the static page.
- **Layout:** cover band at a fixed 16:5 with explicit dimensions and an overlapping avatar; cards in a grid of one, two then three columns with the first card spanning two columns at three, equal height from the grid; empty image slots show a short hatch pattern; the timeline alternates on a center rail from 768 px and runs on a single left rail below, every block in the same order (employer heading, title label, era node).
- **Images:** sources committed under `assets/images`; `scripts/images.mjs` emits AVIF with a WebP fallback at fixed sizes under `public/images` and writes the dimensions to `src/content/images.ts`; origins in `public/images/SOURCES.md`. Missing card images were captured from the owner's own work (the live viewer, a repository screenshot, real CLI output), never downloaded from third parties.
- **Security headers:** `scripts/headers.mjs` writes `out/_headers` after every build. Directives and why: `default-src 'self'` (everything is same-origin); `script-src 'self'` plus a SHA-256 hash per inline script found in the export, so Next's inline payload runs without `'unsafe-inline'`; `style-src 'self'` (the stylesheet is external, D10); `img-src 'self' data:` (own images, data URIs for generated icons); `font-src 'self'` (self-hosted fonts); `connect-src 'self'` (prefetches); `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`, `frame-ancestors 'none'` (no plugins, no base hijack, no forms, no framing); `upgrade-insecure-requests`. Plus `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` denying camera, microphone, geolocation and interest-cohort. Cache: `/_next/static/*` immutable for a year (content-hashed names); `/images/*` one day with a week of stale-while-revalidate (names are not hashed).
- **Gates:** axe at 390, 768, 1280 and 2560; CLS 0 asserted in e2e; a test that no file under `src/` uses `'use client'` or `useEffect`; Lighthouse CI on every PR with accessibility, best practices and SEO at 1.0 as errors, metric budgets as errors (FCP 1.5 s, Speed Index 2 s, TBT 200 ms, CLS 0) and the performance category as a warning at 0.95; a monthly link check. JavaScript budget, measured on the home export (gzip): React DOM, the React Flight client and the Next app router, bundled together by Turbopack in two chunks, 116.8 KB; Next runtime helpers, 27.0 KB; inline RSC payload (page data in `<script>` tags), 11.4 KB; site code, 0 KB (every component is a Server Component); polyfills, 39.6 KB in a `nomodule` chunk that evergreen browsers never load. External scripts total 143.8 KB, so the budget is 150 KB: this is the cost of choosing Next over a zero-JS framework for its hiring signal (D1), and the e2e guard holds that line so a dependency or island cannot grow it unnoticed. LCP budget: 2.0 s on throttled 4G (Google's good threshold is 2.5 s). The mobile LCP element is the About paragraph; it paints at first paint (140 ms unthrottled, 1.9 s under DevTools throttling, performance 98). Lighthouse's simulated mobile score (93, LCP 3.2 s) is a known text-LCP artifact: the simulation charges a text LCP for every script that finished before first paint on localhost, which is all of them. CI therefore keeps the performance category as a warning and FCP, Speed Index, TBT and CLS as errors.
- **Amendment (2026-10-05):** body text is pinned at 16px with a 1.65 line height instead of the fluid clamp, and a 15px secondary step (`--text-small`, 1.55) carries the project blurbs, timeline descriptors and highlights and the 404 line, after the first live review at 2048px found 18px prose too large. The display, heading and label scales stay fluid.
- **Amendment (2026-10-06, the Konami egg):** the one user-triggered animation, as a third island on the D17 loader. The island loads on the first `keydown` on the window (one passive listener, attached once; it collects every key pressed until the island listens for itself, and the island replays them in order, so a first attempt typed while the chunk arrives is not lost), so nothing is requested before a key is pressed; the trigger window tells its chunk apart from the idle WebMCP island. The detector is fifteen lines in `src/lib/konami.ts` (unit-tested: the sequence, a wrong order, a reset after a miss, modifier keys ignored, the letters in either case); the previous site's detector library was 1.5 KB for the same lines and its emoji burst is ruled out by the no-emoji rule, so neither returned and there is no new dependency. Size ceiling 3 KB gzipped for the chunk, asserted as the `konami` lazy budget. Payoff: the 404's UFO-and-cow drawing rises from the bottom-right corner, floats for four seconds on the existing `float` keyframe and leaves (5.5 s in all), with the 404 line "The cow is fine." as a mono toast beside it; the line is the second sentence of the 404 copy, now its own content field so the page and the egg share it. The drawing is the one existing SVG, requested as a plain image only when the sequence completes, so it stays out of the script budget. The payoff is position fixed, `pointer-events: none`, `aria-hidden`, adds no anchor and nothing focusable, never touches the hero, and changes no layout, so CLS stays 0 (asserted after the payoff). Under `prefers-reduced-motion` it fades in place over the same time and the drawing does not float. Repeating the sequence while it shows does nothing until it has left. The home page holds the zero-size island slot at the end of `main`.
- **Consequences:** The `visual-check` skill is the review step before any UI PR. Changing the accent is one token block; changing a heading is one string. Every inline script Next adds in a future version is hashed automatically, so the CSP never loosens by accident.

## D16: DESIGN.md is the design authority, and it describes what ships

- **Date:** 2026-10-05 · **Status:** default
- **Context:** The design rules lived in three places: D14 and D15 here, `docs/design-notes.md` (the Phase 3b study) and the comments in `globals.css`. An agent writing UI had to read all of them and still had no machine-checkable token list. The DESIGN.md format (YAML front matter of tokens plus eight canonical prose sections, with a linter) gives one file to read first and a check that it is well formed.
- **Decision:** `DESIGN.md` at the repo root holds the tokens as `globals.css` defines them (the slate palette in both schemes, the Ultraviolet accent set, Geist and Geist Mono, the fluid type scale with each level's floor, the radius scale as multiples of `--radius`, the spacing the page is built with, the five review breakpoints) and the composition, motion policy and component inventory from D15, in the eight sections, opening with "Read this before writing any UI. Every line here should change what you build." That line is the editing rule: anything that would not change a decision is cut. The Phase 3b study stays in `docs/design-notes.md` as the record behind D15; `DESIGN.md` holds only the rules. `npm run design:lint` runs the format's linter inside `npm run check`; its two contrast warnings on the chip components are false positives (it cannot composite the translucent accent fill over the page), while axe measures the rendered result.
- **Direction:** the document describes the design that is merged on `main`; it does not get ahead of the code. Where the code and a tidier rule disagree, the document says what the code does. A change to `DESIGN.md` that would alter rendering is a design change: it ships as its own PR with before and after visual-check screenshots, and the document is updated in that PR. A documentation PR changes no pixels (`AGENTS.md`).
- **What went wrong first:** the first pass of this branch wrote the rules the author wanted (a 13px type floor, two weights, accent on the primary action, links and rail only, one shadow level, literal radii by element type, a 75rem frame) and then changed the components and `globals.css` to satisfy them, with an e2e check for the type floor. That inverted the relationship: the approved D15 composition was being redesigned through a documentation change, without a design review and without before and after screenshots. It was reverted before merge; the branch now has zero visual difference from `main`, verified by a pixel comparison of the visual-check captures at 390, 1024, 1440 and 2560 px in both schemes.
- **Single source of tokens:** the CLI's exporters were tried first. They convert oklch to hex, cannot express the dark scheme (one flat map of colours) and reject `clamp()` as a font size, so a generated `tokens.css` would be lossy and could not drive `globals.css`. Instead `src/styles/tokens.test.ts` parses the front matter and asserts every colour (light and `-dark`), fluid level, type floor and line height equals its value in `globals.css`, resolves each `calc(var(--radius) * n)` radius against the front-matter value, and checks the spacing tokens against the utilities the home page uses; the `accent*` tokens map to `--brand*` because shadcn reserves `--accent` for hover surfaces. The fluid `clamp()` values live in a `fluid` map (the linter ignores unknown keys whose values are not token-like) and each `typography` token holds the level's floor. Breakpoints are unitless numbers under `breakpoints`. `src/styles/no-hex.test.ts` fails on a hex colour anywhere under `src/` except the stylesheet, the manifest and the Open Graph image (both built outside the stylesheet).
- **Consequences:** Changing a token means editing `DESIGN.md` and `globals.css` together, and the unit test says which one was missed. `AGENTS.md` and the styling rule point at `DESIGN.md` first. D14 and D15 remain the history; `DESIGN.md` is the current description.

## D17: WebMCP tools, the agent-facing JSON and the island loader

- **Date:** 2026-10-05 · **Status:** default
- **Context:** Phase 4 adds the first client code to a page that shipped 0 KB of site JavaScript. Spec §7 wanted in-page WebMCP tools and a machine-readable profile; D12 kept the full resume in the content files for exactly this. Everything had to land without moving the 150 KB initial budget, CLS 0 or the strict CSP, and the WebMCP API itself is a W3C Community Group draft that has already moved once (`navigator` to `document`).
- **Agent-facing data:** `src/lib/webmcp/profile-data.ts` builds one plain object from the content at build time: identity, summary, the first three long About paragraphs (the fourth, about the restructuring, stays out), a structured `availability` entry (`open`, `roles`, `location`, sourced from a new content export so the content guard covers it), the five skill groups, every era and earlier role newest first with every bullet and reference, the projects with descriptions and links, open source, education, the public contact only (email, LinkedIn, GitHub, npm, the location line; the schema is strict so a phone could never pass) and an absolute resume URL. `src/lib/webmcp/profile-schema.ts` composes the zod schema from the content schemas and converts it with `z.toJSONSchema`. Two `force-static` route handlers write `out/api/profile.json` (13.4 KB raw, 4.7 KB gzipped) and `out/api/profile.schema.json`; `scripts/headers.mjs` adds `Access-Control-Allow-Origin: *` and a one-hour cache to `/api/*`. `/llms.txt` is now generated by a route handler from the same content (section anchors, the resume, the JSON and its schema, the tool names) and the hand-written public file is gone.
- **Tools:** eight read-only tools in `src/lib/webmcp/tools/`, one file and one test each, over one contract (`types.ts`): a JSON Schema literal for the input, a pure handler from the data and the input to a result whose text is the JSON of its structured content. Results are deep copies, so a caller cannot reach the shared data; the two lookup tools answer a missing or unknown id with a readable failure that lists the valid values; `callTool` is the one never-throw guard. Nothing under `tools/` imports zod or the content modules, and the index test enforces it, so zod never reaches the browser. The eight files were written by the dynamic-workflow demo (`docs/workflows/webmcp-tools.mjs`, record in `docs/demos/workflow-webmcp-tools.md`): eight Sonnet workers in parallel and one Opus review, whose findings (result aliasing, an untested missing-id path, a dead try/catch, an overpromising description, a weak import guard) were applied by hand.
- **Island loader:** `src/components/islands/island.tsx` is the one hydrated file. It holds the `next/dynamic` entries with `ssr: false` (a Server Component cannot hand a loader function to the client) and arms each island's trigger from a React 19 ref callback, so there is no effect hook anywhere under `src/`. The WebMCP island loads after the load event and the first idle period (2 s timeout). The `'use client'` guard in `e2e/budgets.spec.ts` became an allowlist of the island directories, each file stating on its second line why it is a client component.
- **Polyfill:** `@mcp-b/webmcp-polyfill` pinned at 5.1.0, loaded by dynamic import only when neither `document.modelContext` nor `navigator.modelContext` exists: 7.8 KB gzipped in the export. `@mcp-b/global` was rejected: it bundles an MCP server and transports at 73.5 KB gzipped. A static check found no `eval` or `new Function` in the polyfill, and the e2e console-error test now waits for registration under the served CSP, which keeps `script-src` to self plus hashes and `connect-src 'self'`, so the same-origin fetch of `/api/profile.json` needs no CSP change. The island fetches the JSON once, on the first tool call, never at idle.
- **Shapes that differ:** the native API (Chromium 153 behind `--enable-features=WebMCP`, secure contexts only) returns `inputSchema` from `getTools()` as a JSON string and lists tools in registration order; the polyfill returns an object and sorts by name. Both expose `executeTool(tool, json)`. The e2e tests normalise both.
- **Badge:** a grey tag that is a button, in a reserved 24 px footer row, rendered only after registration succeeds; the explanation is a native popover toggletip (no Base UI JavaScript, keyboard operable, top layer). The chip class strings dropped their class merge so the island does not pull tailwind-merge into its chunk.
- **Budgets measured on the export:** initial JavaScript 143,888 bytes gzipped (143.9 KB) against the 153,600-byte line, up 2.3 KB for the loader; "initial" is now defined in the test as the module scripts and script preloads the HTML references plus every script fetched before the load event with no interaction. Lazy sets, each asserted on its own trigger: the WebMCP island chunk 2.2 KB against 10 KB, the polyfill 7.8 KB against 12 KB (asserted absent in the native project), the JSON 4.7 KB against 24 KB. CLS 0 is asserted before and after the island mounts. Islands are told apart by when they load, not by chunk name, which is why every island needs a distinct trigger.
- **Testing the native branch:** Playwright Test cannot list page-registered tools (that is the Playwright MCP server, which itself evaluates `getTools()` in the page), so the e2e test does the same from inside the page. A fifth Playwright project launches Chromium with `--enable-features=WebMCP` and runs the WebMCP and budget specs against the native API; the four default projects exercise the polyfill. The switch was found by probing Playwright's bundled Chromium: the API is absent without it and on `data:` URLs, present with it on localhost.
- **Origin trial:** the layout emits `<meta http-equiv="origin-trial">` only when `WEBMCP_ORIGIN_TRIAL_TOKEN` is set at build; `deploy.yml` reads it from a repository variable, not a secret, since a token is bound to the origin and public.
- **Consequences:** adding a tool is one file and one test plus a line in `tools/index.ts`; `llms.txt` and the JSON follow the content automatically. The next islands (D18, the Konami egg) register in the loader's map with their own trigger and their own lazy budget. `AGENTS.md` and the README budget table carry the new definition.

## D18: Skills cloud in the Toolbox column, the chips by default and the cloud on the toggle

- **Date:** 2026-10-05 · **Status:** default
- **Context:** Spec §2 reserved one flourish, a React Three Fiber cloud of the Toolbox terms, "built in Phase 4 so it never blocks launch". It had to load after idle, never move LCP or CLS, leave the chips as the scannable and screen-reader version, follow the motion policy, and ship as the second island on the D17 loader.
- **Placement history:** three placements were mocked on the real export with a static, pre-laid-out sphere and screenshotted at 390, 1024, 1440 and 2560 in both schemes (`.visual/mockups/cloud-*.html`, captures under `.visual/cloud-*`): B, the cloud under the chips in the Toolbox column; C, a full-frame band between the About/Toolbox row and the Selected-work hairline; D, the cloud under the About paragraphs. B left the About column about 500 px shorter than the chips at 1024 and 1440. C stretched the sphere into a 16:5 band and read as an unlabelled section. D balanced the columns within 107 to 159 px but showed the same terms twice in one row, once as chips and once as the cloud, and was rejected for that. The decision is none of the three: the cloud takes the Toolbox column itself as the primary view, in the box the chips already occupy, with the chips as the fallback. The terms appear once; the box is the larger of the chip block and a square of the column width (a container query), so it never changes size.
- **The chosen trade:** three and fiber ship as one lazy chunk of 244,301 bytes gzipped (fiber imports all of three, so the minimal-scene figure of 134 KB does not apply; 189 KB three, 57 KB fiber, about 3 KB island). The flourish exists to demonstrate React Three Fiber, and the chunk loads only for a visitor who presses Cloud, so the size is accepted and held by the `cloud` lazy budget of 260 KB in `e2e/budgets.spec.ts`. The initial JavaScript moved by 430 bytes (the loader entry). Sprites over `troika-three-text`: the labels are canvas textures drawn in the page's mono font, so no second font download and no SDF worker (troika would have been 43 KB plus a font file).
- **Reversal (amendment, 2026-10-06):** an outside, non-technical reader preferred the list as the default and the cloud as an option, so the chips are now the default view and the cloud loads only on the Cloud toggle, which also removed the intent gate (idle, 200 px, one input event, the reduced-data and saveData checks) and its tests.
- **Trigger:** the cloud loads only on the Cloud toggle. Once the page has hydrated and a WebGL context can be created, the Toolbox view renders the List/Cloud control into the heading row with List pressed; pressing Cloud requests the chunk, and the button reads `aria-busy` until the canvas exists. The control does not wait for fonts: the heading row reserves its slot server-side, a fixed 144 by 28 px box at the right edge, wide enough for both labels in any face (the longer label measures 60.6 px in the Arial-based fallback and 42.3 px in Geist Mono at 13 px), its content justified to the end so the buttons sit flush with the column edge and the spare width lives on the slot's left; the slot never changes size, so the control's appearance moves nothing, and the labels inside it may re-flow at the font swap like the chip rows inside the reserved box, with both boxes asserted unchanged (a right-anchored control that took its width from the face shifted 0.0001 in the delayed-font case, which now snapshots after the control has mounted; an e2e blocks the font files entirely and expects the control within a second of load). Nothing else requests it: not load, idle, a scroll, a hash arrival at `/#skills`, a wheel, a hover or a key, which the e2e pins at every viewport. Without JavaScript or WebGL there is no control. Under `prefers-reduced-motion` the control works and the cloud shows on press but does not turn on its own; a drag still rotates it. The island pauses the frame loop when the box leaves the viewport, on `visibilitychange` and in List view; hovering never pauses it.
- **Fallback states, all the same picture:** no JavaScript, no WebGL, a load error and a mount error leave the chips visible with nothing to undo; an error boundary around the scene renders nothing. Once the cloud has mounted, the chips fade to opacity 0 and ignore the pointer but stay in the DOM and the accessibility tree (never `display: none` or `visibility: hidden`); the overlay is `aria-hidden`, so the canvas is out of the tree. The List/Cloud control (two real buttons with `aria-pressed`, labels from `src/content/site.ts`) sits in the heading row from hydration on, List pressed; List fades the chips back and pauses the cloud. Nothing is persisted.
- **Rendering:** plain WebGL renderer, device pixel ratio capped at 1.5, no postprocessing, an orthographic camera so world units are CSS pixels. Fibonacci-sphere layout in `src/lib/cloud/layout.ts` (unit-tested), depth expressed mainly by colour (foreground at the front to muted-foreground at the back, read from the tokens at mount and re-read on scheme change) with size held between 13 and 16 px so no term renders below the floor. Rotation 0.12 rad/s.
- **Islands and content:** the island receives the terms and the control labels as props from the Server Component and imports nothing from `src/content`; the same rule now applies to the WebMCP island (badge copy as props, data from `/api/profile.json`) and to any later island. `src/components/islands/no-content-imports.test.ts` fails on such an import, and the budget spec asserts the cloud chunk contains no About paragraph and not the public email.

The portal now sits beside the overlay, not inside it. The first mockups also overlapped labels, as any flattened sphere does; the built cloud depth-orders and rotates them.
- **Interaction (amendment, 2026-10-05):** pointer drag rotates the cloud at 0.005 rad per px (a full turn in about 1,250 px), `grab` and `grabbing` cursors, the tilt clamped to a readable band. Touch rule: the canvas has `touch-action: pan-y`, so vertical pans on touch scroll the page natively and never reach the drag handler; pointer capture is not taken on pointerdown but only once the pointer has moved more than 8 px with horizontal movement exceeding vertical, and it is released on pointerup, pointercancel or lostpointercapture; a touch pointer rotates on the horizontal axis only, a mouse on both; a vertical-dominant gesture on touch leaves the rotation untouched and scrolls the page. The phone-project e2e pins both: a vertical swipe starting on the canvas scrolls the page by about the swipe distance and leaves the rotation to the idle turn, and a horizontal swipe rotates it by about a radian without scrolling. While a drag lasts the idle rotation is suspended; on release the drag velocity decays with a 0.33 s time constant (under 5% after a second) and the idle rotation resumes at once. A pointer that rested before release carries no inertia. Hover does not pause the rotation. The drag record is a small pure object with methods in `src/lib/cloud/drag.ts` (unit-tested), shared between the island's handlers and the frame loop, no dependency; the cloud chunk measured 244,863 bytes gzipped after it, against the 260 KB budget.
